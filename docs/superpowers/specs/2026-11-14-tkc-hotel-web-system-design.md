# แนวทางออกแบบเว็บไซต์และระบบฐานข้อมูล TKC Hotel

วันที่ 14 พฤศจิกายน 2026

## เจตนาและเหตุผล

สร้างระบบโรงแรมจำลองสำหรับวิชา Web Development and Database ให้เพื่อนเข้าใช้งานร่วมกันจากที่ใดก็ได้ หน้าเว็บต้องช่วยให้ทีมเข้าใจ HTML, CSS และ JavaScript พื้นฐาน พร้อมเห็นการแบ่งหน้าที่ของ Node.js และ MySQL ชัดเจน ระบบต้องทำงานตามข้อกำหนดทั้งหมดใน `../../reference/TKC_Requirements_Business_Rules_TH.docx` โดยใช้ข้อมูลโรงแรมและข้อมูลตัวตนสมมติ บริการที่ต้องจ่ายเงินจำลองขั้นตอนและสถานะเท่านั้น ไม่มีการตัดหรือคืนเงินจริง

เอกสาร DOCX ข้างต้นเป็นแหล่งกฎหลัก หาก PDF, Figma หรือเว็บต้นแบบเดิมระบุไม่ตรง ให้ยึด DOCX เอกสาร PDF ช่วยอธิบายบริบท ส่วน [Figma ของทีม](https://www.figma.com/design/i4g6ghZqkT92dG2jPTeKUR/) และหน้าเว็บเดิมใช้เป็นข้อมูลอ้างอิงเรื่องลำดับการใช้งานและฟีเจอร์

## เป้าหมาย

- ให้สมาชิกสมัคร เข้าใช้ ค้นหาห้อง จองหลายห้อง เลือกบริการ ดูราคาและสถานะ และดำเนินการหลังจองได้จริงกับข้อมูลร่วมกันใน MySQL
- ให้ Superadmin ฝ่ายต้อนรับ ฝ่ายบัญชี ฝ่ายบริหาร และแม่บ้านทำงานตามสิทธิ์ของตน โดยการเปลี่ยนข้อมูลของฝ่ายหนึ่งปรากฏแก่ฝ่ายที่เกี่ยวข้อง
- บังคับกฎการกันห้อง ราคา การชำระแบบจำลอง การเข้าพัก การคืนเงิน และประวัติการดำเนินงานที่เซิร์ฟเวอร์ เพื่อให้ผู้ใช้หลายคนทำงานพร้อมกันได้สอดคล้องกัน
- ครอบคลุม REQ, UR และ BR ทุกข้อใน DOCX ทั้งในหน้าจอ ขั้นตอนทำงาน และข้อมูลที่เก็บ โดยใช้เอกสารนั้นเป็นเกณฑ์ตรวจรับรายละเอียด
- จัดโครงสร้างไฟล์และฐานข้อมูลให้ทีมปี 1 อ่าน แก้ไข และอธิบายความสัมพันธ์ได้

## สิ่งที่ไม่ใช่เป้าหมายและสิ่งที่ต้องหลีกเลี่ยง

- ไม่มีการรับเงินจริง เชื่อมธนาคาร payment gateway หรือโอนเงินจริง แม้หน้าจอจะแสดงจำนวนเงินและสถานะ
- โรงแรมและห้องพักเป็นข้อมูลจำลอง ไม่มีการยืนยันห้องจริงนอกระบบงานวิชา
- ไม่บังคับให้เพื่อนกรอกเลขบัตรประชาชนหรือพาสปอร์ตจริง ช่องข้อมูลนี้ใช้ข้อมูลสมมติตาม BR-25
- ไม่ใช้ React, Tailwind หรือ TypeScript ใน frontend นี้
- ต้องไม่แสดงธุรกรรมจำลองราวกับเป็นการจ่ายเงินจริง และต้องไม่ใช้การซ่อนปุ่มใน browser แทนการตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์
- ต้องไม่เก็บรายการจองเฉพาะในหน่วยความจำของ browser หรือใช้ตัวเลขสรุปที่ hardcode แทนข้อมูลจาก MySQL

## แนวทางที่พิจารณา

| แนวทาง | ข้อดี | สิ่งที่แลก |
| --- | --- | --- |
| **เลือก: หน้า HTML แยกตามงาน ใช้ vanilla JavaScript เรียก Node.js API และ MySQL** | เห็นเส้นแบ่ง browser, server และ database ชัด; เหมาะกับการเรียนพื้นฐาน; งานแต่ละฝ่ายแยกไฟล์และตรวจได้ | ต้องเขียนการดึงข้อมูลและแสดงผลใน browser มากขึ้น |
| Node.js สร้าง HTML ผ่าน template เช่น EJS | ฟอร์มและหน้าแสดงข้อมูลบางส่วนเขียนสั้นลง | เพิ่มภาษา template และต้องออกแบบการอัปเดตหน้าเมื่อข้อมูลเปลี่ยนบ่อย |

การต่อเติมเว็บหน้าเดียวเดิมโดยเพิ่มเงื่อนไขทั้งหมดใน `script.js` ไม่เหมาะกับจำนวนบทบาทและกฎใน DOCX จึงไม่เลือกเป็นแนวทางหลัก เว็บเดิมใช้เป็นรายการพฤติกรรมที่ต้องตรวจเทียบระหว่างย้ายระบบ

## โครงสร้างผลิตภัณฑ์และหน้าจอ

ใช้เว็บสาธารณะกับพื้นที่พนักงานเป็นสองส่วนที่แยกเมนูและบริบทงาน แต่ใช้ข้อมูลชุดเดียวกันจาก API และ MySQL

**ส่วนลูกค้า**

1. หน้าหลัก: ภาพโรงแรมพร้อมช่องค้นหาวันเข้า วันออก และจำนวนคน; ทางไปประเภทห้อง บริการ รีวิว สถานที่แนะนำ และติดต่อ
2. ผลค้นหาและรายละเอียดห้อง: แสดงประเภทห้อง ราคา ความจุ และจำนวนที่ว่าง *ตามช่วงวันที่* ไม่ใช้สถานะห้องวันนี้เป็นคำตอบแทน
3. ขั้นตอนจอง: เลือกหลายห้องต่างประเภทโดยใช้วันเข้าออกเดียวกัน; เลือกอาหารเช้า ฟิตเนส ซาวน่า และรอบเที่ยว; เห็นราคาหลังโปรโมชั่น ยอดรวม มัดจำหรือยอดเต็มก่อนยืนยัน
4. การชำระแบบจำลอง: ผู้ใช้เลือกรูปแบบการชำระและส่งหลักฐานตัวอย่างหรือใช้ขั้นตอนออนไลน์จำลอง จากนั้นติดตามผลตรวจอัตโนมัติจำลองและผลรับรองจากฝ่ายบัญชี
5. บัญชีสมาชิก: สมัครและเข้าสู่ระบบ ดูรายการจอง ยอดคงเหลือ สถานะ แจ้งยกเลิก แจ้งมาช้า แชตฝ่ายต้อนรับ และเขียนรีวิวเมื่อมีสิทธิ์

**ส่วนพนักงาน**

- Superadmin: ประเภทห้อง ห้องจริง ราคาและความจุ; จัดและเปลี่ยนห้องหลังบัญชียืนยัน; สถานที่ตามฤดู; ลบรีวิวพร้อมเหตุผล; จัดสิทธิ์พนักงานที่อนุญาต; ติดตามการตรวจเงินเกิน 30 นาที
- ฝ่ายต้อนรับ: สถานะและประวัติห้อง; Walk-in; ตรวจเงื่อนไข Check-in และ Check-out; บริการเพิ่มหลังเข้าพัก; รอบเที่ยวและผู้ร่วม; การมาถึงช้า; แชต; รายงานแม่บ้าน
- ฝ่ายบัญชี: รายการชำระและหลักฐานจำลอง; รับรองหรือปฏิเสธ; ยอดมัดจำ ยอดค้าง และธุรกรรม; เสนอคำขอคืนเงินและบันทึกการคืนที่อนุมัติ; ประวัติแก้ไขข้อมูลการเงิน
- ฝ่ายบริหาร: ภาพรวมและรายงาน; โปรโมชั่น; ประวัติทุกฝ่าย; สิทธิ์ทุกฝ่ายรวม Superadmin; ปิดเปิดห้องซ่อม; อนุมัติคืนเงินและย้ายห้องหลัง Check-in
- แม่บ้าน: คิวที่เกิดจาก Check-out; เริ่มและยืนยันงานทำความสะอาดพร้อมผู้ทำและเวลา; รายงานความเสียหายพร้อมรูป

ทุกหน้าพนักงานใช้ shell ร่วมกันที่มีเมนูตามบทบาท ชื่องาน สถานะ และตารางค้นหา/กรอง แต่แสดงเฉพาะงานของบทบาทนั้น หน้าเน้น “งานที่ต้องทำ” และสถานะที่อ่านได้เร็วบนมือถือกับคอม

## ภาพลักษณ์ที่เลือก

ใช้โครงแบบ **A Blue Harbor** จากแบบร่างที่ผู้ใช้เลือก: ภาพโรงแรมเด่นบนหน้าแรก แถบค้นหาที่มองเห็นทันที พื้นสีน้ำเงินเข้มกับพื้นผิวสีขาว และหน้า staff ที่ใช้แถบเมนูน้ำเงินเข้มกับพื้นที่งานสีขาว เปลี่ยนสีเน้นของ A จากทองอ่อนเป็น **ส้มปะการังของแบบ B** สำหรับปุ่มหลักและจุดที่ต้องลงมือ สีสถานะสำเร็จ รอตรวจ ผิดพลาด และปิดซ่อมต้องมีข้อความกำกับ ไม่ใช้สีอย่างเดียว

Frontend ต้องดูประณีตและมีคุณภาพสูงกว่าภาพร่าง: ภาพหลักต้องคัดเลือกให้สื่อบรรยากาศโรงแรมจริง จัดลำดับตัวอักษรและพื้นที่ว่างอย่างตั้งใจ ใช้ภาพและรายละเอียดห้องเพื่อช่วยตัดสินใจจอง และให้ปุ่ม ฟอร์ม ตาราง และสถานะมี feedback ที่ต่อเนื่อง เว็บลูกค้าเน้นอารมณ์การพักผ่อน ส่วน dashboard พนักงานเน้นความชัดเจนและงานที่ต้องทำ ทั้งสองส่วนใช้ระบบสีและองค์ประกอบร่วมกัน ไม่เติมลูกเล่นจนทำให้การจองหรือการอ่านข้อมูลช้า

ใช้ [21st.dev](https://21st.dev/) เป็นเรฟด้านรูปแบบและปฏิสัมพันธ์ของ component เท่านั้น เพราะไลบรารีต้นทางเผยแพร่โค้ด React, TypeScript และ Tailwind ซึ่งไม่ตรงกับ stack ที่เลือก ให้เขียนผลลัพธ์ด้วย HTML, CSS และ JavaScript ของโปรเจกต์เอง และให้แหล่งภาพ/ฟอนต์ที่นำมาใช้มีสิทธิ์ใช้งานชัดเจน

ค่ารหัสสี ชุดตัวอักษร ระยะห่าง และส่วนประกอบร่วมเป็นการตัดสินใจของผู้สร้างในขั้นทำงาน โดยรักษาน้ำเงิน ขาว และส้มปะการังที่ตกลงแล้ว หน้าเว็บและ dashboard ต้องรองรับจอมือถือและคีย์บอร์ด ใช้ label, ข้อผิดพลาด และสถานะโหลดที่เข้าใจได้ การเคลื่อนไหวต้องมีหน้าที่ช่วยสื่อสถานะและเคารพการตั้งค่าลดการเคลื่อนไหว

## สถาปัตยกรรมและการจัดไฟล์

ข้อเสนอการลงมือทำคือ HTML หลายหน้า, CSS ร่วมที่ใช้ตัวแปรสี, JavaScript แบบ ES modules, Node.js กับ Express สำหรับ API และ MySQL สำหรับข้อมูลถาวร Express ทำหน้าที่เสิร์ฟไฟล์หน้าเว็บด้วย แต่กฎราคา สิทธิ์ และการเปลี่ยนสถานะอยู่ใน server ทั้งหมด หน้าเว็บเรียก API และแสดงผล; MySQL เป็นแหล่งข้อมูลเดียวของยอดและสถานะ ข้อเลือก Express เป็นข้อเสนอของผู้สร้างภายใต้ Node.js ที่ทีมเลือก ไม่ใช่ข้อกำหนดจากผู้ใช้

จัดโค้ดตามความรับผิดชอบ เช่น `public/` สำหรับ HTML/CSS/JS, `server/routes/` สำหรับปลายทาง API, `server/services/` สำหรับกฎธุรกิจ, `server/repositories/` สำหรับคำสั่งฐานข้อมูล, `db/migrations/` สำหรับโครงสร้างตาราง และ `db/seeds/` สำหรับข้อมูลเริ่มต้น ตัวอย่างบัญชีและห้องพักต้องสร้างด้วย seed ที่รันซ้ำได้อย่างควบคุม ไม่ฝังรหัสผ่านหรือข้อมูลตัวอย่างใน JavaScript ฝั่ง browser

เซิร์ฟเวอร์ตรวจผู้ใช้และบทบาททุกคำขอที่อ่านหรือเปลี่ยนข้อมูลเฉพาะสิทธิ์ รหัสผ่านเก็บแบบ hash; session ใช้ cookie ที่ตั้งค่าอย่างปลอดภัย ไม่ให้ client ระบุบทบาทของตัวเอง การเปลี่ยนข้อมูลที่มีผลต่อจำนวนห้อง ที่นั่งเที่ยว ยอดเงิน หรือสถานะต้องทำใน transaction และล็อก/ตรวจข้อมูลที่เกี่ยวข้องก่อนบันทึก เพื่อป้องกันผู้ใช้หลายคนยืนยันชนกัน คำตอบ API ต้องแยกข้อผิดพลาดที่แก้ได้ เช่น ห้องเต็มหรือหมดเวลากันห้อง ออกจากข้อผิดพลาดระบบ

ไฟล์หลักฐานชำระเงินและรูปความเสียหายเป็นไฟล์ตัวอย่างที่มีข้อจำกัดชนิดและขนาด เก็บไฟล์ในพื้นที่ถาวรของ server พร้อมข้อมูลอ้างอิงใน MySQL รูปแบบ storage ตอนนำขึ้นโฮสต์เป็นเรื่องที่คุยภายหลัง แต่ต้องไม่อาศัยหน่วยความจำชั่วคราวของ browser หรือ server

## กลุ่มข้อมูลหลักใน MySQL

- คนและสิทธิ์: ลูกค้าแยกจากบัญชีสมาชิก; พนักงาน แผนก บทบาท และ session
- ห้องและการจอง: ประเภทห้อง ห้องจริง ช่วงปิดซ่อม การจอง รายการห้องที่จอง การกันจำนวนชั่วคราว ประวัติการจัด/ย้ายห้อง และลำดับสถานะ
- ราคาและเงินจำลอง: โปรโมชั่นและ snapshot ที่ใช้จริงต่อการจอง รายการบริการ รายการชำระ หลักฐาน ผลตรวจ คำขอคืนเงิน ผลอนุมัติ และรายการคืนเงินจำลอง
- บริการและงาน: วันอาหารเช้า ชุดฟิตเนส/ซาวน่าต่อทุกห้อง รอบเที่ยว ผู้ร่วมเที่ยว งานทำความสะอาด และรายงานเสียหาย
- การสื่อสารและตรวจสอบ: ข้อความแชต รีวิวและข้อมูลการซ่อน สถานที่แนะนำตามฤดู และ audit log พร้อมผู้ทำ เวลา เหตุผล และค่าก่อน/หลัง

ตารางจริงและคีย์ต่างประเทศให้ได้จาก ER Diagram และ migration ในขั้นวางแผน โดยรักษาความสัมพันธ์ตาม BR-1 ถึง BR-74 ข้อมูล 800 ห้องเป็น seed ตามจำนวนและรหัสใน DOCX ไม่ใช่ 800 การ์ดที่ render พร้อมกัน

## กฎที่กำหนดพฤติกรรมข้ามหน้าจอ

- **ห้องและวัน:** ช่วงเข้าพักใช้วันเข้าแบบรวมและวันออกแบบไม่รวม ห้องหนึ่งจองทับช่วงเดียวกันไม่ได้ ต้องนับรายการกันห้องที่ยังไม่หมดอายุ ห้องรอทำความสะอาดรับจองอนาคตได้แต่ Check-in ไม่ได้ก่อนทำเสร็จ ห้องปิดซ่อมรับจองหรือ Check-in ในช่วงปิดไม่ได้
- **การจอง:** หนึ่งรายการมีอย่างน้อยหนึ่งห้องต่างประเภทได้ ทุกห้องใช้วันเดียวกัน ระบบกันจำนวนตามประเภทก่อนจัดเลขห้องจริง; Superadmin จัดห้องหลังบัญชียืนยัน ฝ่ายต้อนรับจัด Walk-in ได้เอง การเปลี่ยนห้องก่อนเข้าพักและการย้ายหลังเข้าพักต้องเก็บเหตุผลและประวัติ
- **ราคา:** ค่าห้องคิดตามจำนวนคืน โปรโมชั่นหลายรายการลดทีละขั้นเฉพาะค่าห้องและบันทึกราคาที่ใช้ บริการคิดตาม BR-41 ถึง BR-46: สระรวมราคา ฟิตเนส/ซาวน่าต่อห้องหนึ่งครั้ง อาหารเช้าต่อห้องต่อวันที่เลือก โดยทุกห้องในใบจองใช้ชุดวันและบริการเหมือนกัน
- **ทัวร์:** รอบตามวันที่รองรับไม่เกิน 10 คนรวมทุกการจอง ครั้งแรกของคนหนึ่งในวันนั้น 50 บาท ครั้งต่อไป 20 บาท ยกเลิกเฉพาะเที่ยวคืนที่นั่งแต่ไม่คืนค่าบริการ
- **เงินจำลอง:** ห้องเดียวมัดจำ 20% หลายห้อง 40% หรือจ่ายเต็ม 100% ของยอดรวมหลังโปรโมชั่นและบริการ; รายการจองมีการชำระได้หลายครั้ง; กันห้อง 15 นาทีเพื่อเริ่มชำระหรือส่งหลักฐาน; หลังส่งหลักฐานกันห้องต่อระหว่างบัญชีตรวจ โดย 30 นาทีเป็นเวลาติดตาม ไม่ใช่เวลายกเลิกอัตโนมัติ
- **เข้าพักและยกเลิก:** Check-in หลัง 14:00 เมื่อยืนยันจอง ชำระครบ และห้องพร้อม; Check-out ก่อน 12:00 ส่งห้องเข้าคิวแม่บ้านทันที; No-show หลัง 06:00 วันถัดไปหากไม่ได้แจ้งช้า; กฎยกเลิกทั้งใบจอง บริการ และการคืนเงินใช้ BR-56 ถึง BR-64 รวมการอนุมัติของฝ่ายบริหารก่อนบัญชีบันทึกคืน
- **โรงแรมให้ห้องไม่ได้:** หากห้องใดในใบจองใช้ไม่ได้ ให้เสนอห้องทดแทนที่รองรับผู้เข้าพักในวันเดิมก่อน โดยไม่เพิ่มยอดที่ลูกค้าต้องจ่าย หากไม่มีห้องที่เหมาะสมหรือลูกค้าไม่รับ ให้ยกเลิกทั้งใบจองและคืนยอดที่ชำระแล้วทั้งหมดแบบจำลองตาม BR-32 โดยผ่านการอนุมัติคืนเงินตาม BR-61
- **สิทธิ์และประวัติ:** รีวิวได้เฉพาะสมาชิกผู้จองหลัง Check-in; ซ่อนรีวิวต้องเก็บเนื้อหาเดิมและเหตุผล; แชตผูกผู้ส่ง/ผู้ตอบและเวลา; การเพิ่ม ลบ แก้ไข และเปลี่ยนสถานะของทุกฝ่ายรวม Superadmin ต้องตรวจย้อนหลังได้

## ข้อกำหนดเสริมสำหรับกรณีที่ DOCX ไม่ระบุขั้นตอนย่อย

ข้อกำหนดต่อไปนี้เป็นข้อเสนอของผู้สร้างเพื่อให้ทำระบบได้ครบและทดสอบได้ โดยไม่เปลี่ยนกฎหลักใน DOCX

- เมื่อการตรวจชำระแบบจำลองอัตโนมัติไม่ผ่าน ผู้ใช้แก้ไขหรือส่งใหม่ได้ภายในเวลากันห้อง 15 นาทีเดิม เมื่อฝ่ายบัญชีปฏิเสธหลังส่งหลักฐาน ให้เริ่มช่วงแก้ไข 15 นาทีใหม่และแจ้งเหตุผลแก่ลูกค้า หากไม่ส่งใหม่ทันเวลา ให้ยกเลิกรายการรอชำระและคืนจำนวนห้อง
- ที่นั่งเที่ยวที่เลือกในขั้นจองต้องถูกกันพร้อมรายการจอง โดยนับรวมในการตรวจเพดาน 10 คนระหว่างช่วง 15 นาทีและช่วงรอบัญชีตรวจ คืนที่นั่งเมื่อรายการหมดเวลา ถูกยกเลิก หรือพ้นช่วงแก้ไขหลังถูกปฏิเสธ
- ฝ่ายบริหารกำหนดโปรโมชั่นเปอร์เซ็นต์ วันเริ่มและสิ้นสุด เงื่อนไขจำนวนคืนขั้นต่ำ/จำนวนห้องขั้นต่ำ และลำดับการใช้เป็นตัวเลข โปรโมชั่นที่มีผลและเข้าเงื่อนไขทั้งหมดใช้ตามลำดับตัวเลขจากค่าห้องคงเหลือ ก่อนบวกค่าบริการ การจองที่ยืนยันแล้วเก็บ snapshot ราคาและลำดับเดิม
- การคืน 80% ของค่าบริการที่ยกเลิกตอน Check-in ไม่เกิดปัญหาการแบ่งมัดจำเข้ารายการบริการ เพราะ BR-13 และ BR-35 บังคับให้ชำระยอดก่อนเข้าพักครบก่อน Check-in จึงทราบค่าบริการที่ชำระแล้วเต็มจำนวน

## วิธีตรวจรับและข้อที่มอบให้ผู้สร้างตัดสินใจ

ก่อนถือว่าเสร็จ ให้ไล่ REQ-01 ถึง REQ-12, UR ทุกบทบาท และ BR-1 ถึง BR-74 เป็น checklist โดยแต่ละข้อมีหน้าจอหรือ API ที่ใช้งานได้ ข้อมูล MySQL ที่พิสูจน์ผล และตัวอย่างสถานการณ์ทดสอบ สำคัญเป็นพิเศษคือผู้ใช้สองคนจองห้องสุดท้ายพร้อมกัน ผู้ใช้สองคนเลือกที่นั่งเที่ยวสุดท้ายพร้อมกัน การหมดเวลากันห้อง การรอตรวจเกิน 30 นาที และการเปลี่ยนโปรโมชั่นหลังยืนยันจอง ผลต้องตรง DOCX

ผู้สร้างตัดสินใจรายละเอียดของ route, schema, migration, session library, รูปแบบ refresh ข้อมูล/แชต, สื่อภาพ, ตัวเลขสีที่เข้าถึงได้ และวิธีจัดแบ่งงานภายในทีม โดยต้องรักษาข้อเลือกที่ผู้ใช้ยืนยันในเอกสารนี้ เรื่องผู้ให้บริการโฮสต์และค่าใช้จ่ายโฮสต์ยังไม่ตัดสินใจ
