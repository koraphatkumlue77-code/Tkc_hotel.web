# Reception Settlement and Service Pass Design

## Intent

ปรับงานฝ่ายต้อนรับให้ค้นหาใบจองด้วยรหัส เลือก Check-in หรือ Check-out เห็นยอดที่ต้องรับจริง แนบเลขอ้างอิงและหลักฐาน แล้วให้ระบบบันทึกการเงิน การเข้าพัก และสถานะห้องพร้อมกัน เพื่อไม่ให้ข้อมูลคนละส่วนขัดกัน

บริการฟิตเนสและซาวน่าเปลี่ยนจากการคิดเงินทุกรอบเป็นสิทธิ์ตลอดการเข้าพัก: ซื้อหนึ่งครั้งต่อคนแล้วจองเข้าใช้รอบต่าง ๆ ได้เรื่อย ๆ ภายในวันเข้าพัก โดยทุกครั้งยังต้องมีที่ว่างในรอบนั้น

## Goals

- ฝ่ายต้อนรับกรอกรหัสการจองและเลือก `CHECK_IN` หรือ `CHECK_OUT` ได้จากฟอร์มเดียว
- ระบบคำนวณยอดที่ต้องรับเอง ห้ามพนักงานแก้ยอดเอง
- การรับเงินต้องมีวิธีชำระ เลขอ้างอิง และไฟล์หลักฐาน
- Check-in เก็บเฉพาะค่าห้องส่วนที่เหลือจากมัดจำ
- Check-out เก็บเฉพาะค่าบริการเสริมที่ยังไม่ได้ชำระ
- การเงิน สถานะ Booking การเข้าพัก และสถานะ Room เปลี่ยนพร้อมกันใน transaction เดียว
- ฝ่ายต้อนรับเห็นบริการและทริปแยกรายการ พร้อมยอดบริการที่เก็บตอน Check-out
- หน้าสถานะห้องกรองได้เฉพาะ `ห้องทั้งหมด` หรือ `ประเภทห้อง`

## Non-goals

- ไม่คิดค่าทริป เพราะทริปทั้งหมดฟรี
- ไม่เพิ่มตัวกรองห้องตามจำนวนผู้พักหรือสถานะห้อง
- ไม่ให้ลูกค้าจ่ายค่าฟิตเนส/ซาวน่าทุกรอบ
- ไม่เปลี่ยนสิทธิ์ของฝ่ายบัญชีในการตรวจสลิปออนไลน์เดิม
- ไม่ทำระบบคืนเงินใหม่ในงานนี้

## Business Rules

### Check-in settlement

1. ใช้ได้กับใบจอง `CONFIRMED` หรือ `LATE_ARRIVAL` ที่มีการจัดห้องครบแล้ว
2. ยอดค่าห้องสุทธิเท่ากับ `room_subtotal_snapshot - discount_total_snapshot`
3. ยอดรับตอน Check-in เท่ากับค่าห้องสุทธิ ลบด้วยยอดรับเข้าที่ตรวจสอบแล้วก่อนหน้า แต่ไม่นำค่าบริการเสริมมารวม
4. มัดจำออนไลน์ต้องคำนวณจากค่าห้องสุทธิ ไม่รวมฟิตเนส ซาวน่า หรือบริการที่ชำระตอน Check-out
5. ถ้ายอด Check-in เป็นศูนย์ ระบบยังทำ Check-in ได้โดยไม่สร้าง Payment ซ้ำ
6. เมื่อสำเร็จ Booking เปลี่ยนเป็น `CHECKED_IN` และห้องที่จัดไว้เปลี่ยนเป็น `OCCUPIED`

### Service passes and round reservations

1. ฟิตเนส 500 บาทต่อคนต่อการเข้าพัก และซาวน่า 300 บาทต่อคนต่อการเข้าพัก
2. การซื้อครั้งแรกสร้างสิทธิ์ของบริการสำหรับห้องที่จองและจำนวนคนที่เลือก จำนวนต้องไม่เกินจำนวนผู้พักในห้อง
3. สิทธิ์ใช้ได้ตั้งแต่วัน Check-in ถึงก่อนวัน Check-out และจองรอบได้หลายครั้งโดยไม่เพิ่มเงิน
4. การจองรอบใหม่ต้องไม่เกินจำนวนคนที่มีสิทธิ์และต้องผ่านข้อจำกัดความจุของรอบ
5. ฟิตเนสจำกัด 40 คนต่อรอบ ซาวน่าใช้เฉพาะจำนวนผู้มีสิทธิ์เพราะยังไม่มีเพดานความจุร่วมที่กำหนด
6. ถ้าต้องการเพิ่มจำนวนผู้มีสิทธิ์ภายหลัง ระบบคิดเฉพาะส่วนต่างจนไม่เกินจำนวนผู้พัก; ไม่ลดจำนวนสิทธิ์หลังมีการใช้งาน
7. ทริปยังคงเป็นการจองรอบฟรี ความจุ 10 คน และไม่เพิ่มยอดค้าง

### Check-out settlement

1. ใช้ได้กับ Booking สถานะ `CHECKED_IN`
2. ยอดรับตอน Check-out คือยอดค่าบริการเสริมทั้งหมดที่ยังไม่ถูกชำระ รวมสิทธิ์ฟิตเนส ซาวน่า และบริการที่มีราคาอื่น ๆ
3. ระบบรวบยอดครั้งเดียว แม้ลูกค้าจะพักหลายวันหรือจองใช้บริการหลายรอบ
4. เมื่อยอดค้างบริการเป็นศูนย์และบันทึกสำเร็จ Booking เปลี่ยนเป็น `CHECKED_OUT` ห้องเปลี่ยนเป็น `NEEDS_CLEANING` และสร้างงานทำความสะอาดตามระบบเดิม

### Payment evidence

1. รายการรับเงินจากฟอร์มนี้มีวิธีชำระ เลขอ้างอิง และไฟล์หลักฐาน PNG/JPEG/WebP
2. เงินสดใช้เลขใบเสร็จและภาพใบเสร็จ; โอนหรือบัตรใช้เลขธุรกรรมและภาพสลิป/หลักฐาน
3. เซิร์ฟเวอร์เป็นผู้คำนวณ amount และ transaction type; ค่าในหน้าเว็บเป็นเพียงการแสดงผล
4. ใช้ idempotency key ป้องกันการบันทึกเงินหรือเปลี่ยนสถานะซ้ำ

## Reception UI

ฟอร์ม `รับชำระและเปลี่ยนสถานะการเข้าพัก` ประกอบด้วย:

1. ช่องรหัสการจองและปุ่มค้นหา
2. ตัวเลือก `Check-in` หรือ `Check-out`
3. สรุปลูกค้า วันที่ ห้องที่จัด สถานะปัจจุบัน และบริการเสริม
4. ยอดที่ต้องรับซึ่งเป็น read-only พร้อมคำอธิบายว่าเป็นค่าห้องหรือค่าบริการ
5. วิธีชำระ เลขอ้างอิง อัปโหลดหลักฐาน และปุ่มยืนยัน
6. ปุ่มยืนยันเปิดใช้งานเมื่อสถานะ ห้อง และหลักฐานครบเท่านั้น

รายการจองด้านล่างต้องแสดงรายละเอียดฟิตเนส ซาวน่า และทริป พร้อม `ค่าบริการที่เก็บตอน Check-out` และยอดรวม

## Room Status UI

- เพิ่ม select หนึ่งช่อง: `ห้องทั้งหมด`, `Standard Room`, `Deluxe Room`, `Superior Room`, `Family Room`
- ตัวกรองเรียกข้อมูลห้องจริงตาม `roomTypeId` และไม่แก้ข้อมูลห้อง
- หลัง Check-in/Check-out สำเร็จ รายการห้องและตัวเลขสรุปต้องรีเฟรชทันที

## Server and Data Design

- เพิ่ม endpoint อ่าน settlement preview จาก booking code และ action เพื่อคืนยอดที่คำนวณจากฐานข้อมูล
- เพิ่ม multipart endpoints สำหรับ Check-in และ Check-out settlement ที่รับ method, reference, proof และ idempotency key แต่ไม่รับ amount จาก client
- ใช้ transaction เดียวล็อก Booking, RoomAssignment, Room, Payment และรายการบริการที่เกี่ยวข้องก่อนบันทึก
- เก็บหลักฐานใน storage เดิมแบบ private และลบไฟล์ถ้า transaction ล้มเหลว
- ใช้ `SERVICE_PAYMENT` สำหรับยอดบริการ Check-out และ `BALANCE` สำหรับค่าห้องคงเหลือ Check-in
- ปรับ service model ให้ BookingService หนึ่งรายการแทนสิทธิ์ต่อห้อง/บริการ และ ServiceUsage หลายรายการแทนการจองรอบ
- migration ต้องเป็น expand-first และมี backup/rollback note ก่อนเปลี่ยน unique constraints ที่เกี่ยวข้อง

## Approaches Considered

### Selected: atomic server settlement

เซิร์ฟเวอร์คำนวณยอด ตรวจหลักฐาน บันทึก Payment เปลี่ยน Booking และ Room ในคำสั่งเดียว ข้อดีคือไม่เกิดเงินกับสถานะห้องค้างคนละขั้น และเหมาะกับการ Demo business rule สด

### Rejected: browser-orchestrated payment then stay action

หน้าเว็บบันทึก Payment แล้วค่อยเรียก Check-in/Check-out แยกกัน ทำง่ายกว่าแต่การเรียกครั้งที่สองอาจล้มเหลว ทำให้รับเงินแล้วสถานะห้องไม่เปลี่ยน จึงไม่ตรงกับข้อกำหนดของผู้ใช้

### Rejected: charge every facility round

คิด 500/300 บาททุกครั้งที่จองรอบ แม้รวมเก็บตอน Check-out ก็ขัดกับกติกาซื้อครั้งเดียวและเข้าใช้ได้ตลอดการเข้าพัก

## Verification

- Integration tests พิสูจน์สูตรยอด Check-in และ Check-out รวมกรณีมัดจำ บริการหลายรอบ การส่งซ้ำ และ concurrent settlement
- Integration tests พิสูจน์ซื้อ pass ครั้งเดียว จองหลายรอบ และความจุ 40 คน
- Browser test ใช้รหัสใบจองจริง แนบหลักฐาน Check-in ตรวจ `OCCUPIED` จากนั้นเพิ่มบริการหลายรอบและ Check-out ตรวจ `NEEDS_CLEANING`
- ทดสอบตัวกรองห้องทั้งหมดและแต่ละประเภทบน desktop/mobile
- Full unit และ database integration suites ต้องผ่านก่อนส่งมอบ
